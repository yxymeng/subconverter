# subconverter 优化路线

日期：2026-10-01。状态：已按用户要求作为本轮开发基线，四阶段代码已实施；Windows 实机与 Docker 镜像验证仍有环境限制。

## 目标与范围

形成适合自己长期使用的版本，Windows 优先并保留 Linux/Docker；服务本机与自己的局域网设备。维持现有订阅 URL 和配置工作流，先解决可靠性与首次转换耗时，再提供轻量 Web 转换入口。

用户通常一份订阅、最多两份，实际外部配置为 yxymeng.github.io 的 `Ruleset/Clash.ini`。现阶段最有依据的性能方向是规则加载与处理：该配置引用 25 个远程规则文件，仅引用的本仓库规则文件已约 3.56 MB、10.5 万行。具体网络和处理耗时仍须测量。

规则缓存有效期内允许复用，过期或主动强刷时等待更新。必需规则集更新失败明确报错，保留旧版供手动选择。见 [ADR-0001](adr/0001-ruleset-freshness-and-failure.md)。

## 建议阶段

### 第一阶段：诊断清楚，下载结果可靠

- 给转换过程增加请求关联标识和分阶段耗时：外部配置、规则下载、订阅下载、解析、规则处理、导出。
- 将下载失败、解析失败和无可导出节点分别报告；显示源站、HTTP 状态或传输错误、缓存状态，默认脱敏。
- 修复中断重试残留正文、失败下载被当作成功写缓存的问题，保留本次 403 修复。
- 明确客户端头与订阅源头的边界，避免无关头继续引发拒绝；自定义 UA 和按源站提供凭据的需求保留。
- 新增少量行为回归，覆盖真实修复和可靠性边界。

验收：模拟 403、200 无效内容、超时和中途断开能得到不同原因；第二次重试的正文只有完整结果；失败不会覆盖上一份正常缓存；诊断输出不含虚构的测试 Token/Cookie/认证值。

### 第二阶段：缩短首次规则加载，保证更新语义

- 在真实 Windows 使用环境测冷缓存、有效缓存、缓存过期和主动强刷四种状态。分别记录总时长、各阶段时长、请求数、下载字节、规则处理量和输出大小。
- 先做最小对照：比较现有 `async_fetch_ruleset=false/true` 的首次转换耗时与资源使用。这是诊断实验，正式实现仍需控制并发上限。
- 若网络等待占主导，优先有上限的规则下载并发、同键请求合并和连接复用；保持规则匹配优先顺序。
- 若规则处理占主导，优先缓存按内容与配置版本区分的规则处理结果；完整输出缓存作为进一步候选，先定义正确的失效条件。
- 有效期内复用；过期/强刷等待必需更新；失败清晰报告并保留上次成功版本，提供显式旧版选择。
- 协调 TOML/INI/YAML 的对应配置项。现有 TOML 读取遗漏 serve_cache_on_fetch_fail，新增策略也应避免只在部分格式生效。

验收：与第一阶段建立的同环境基线比较，首次总耗时下降；有效缓存请求不重复下载；必需规则失败时不静默生成缺少规则的配置；输出节点和规则匹配优先顺序不变。具体速度目标在基线测量后设定。

现阶段不直接删除大型规则，也不承诺固定倍数。大型广告规则和国内规则是否裁剪应结合实际分流需求；对不同代理分组盲目合并或排序可能改变匹配结果。

### 第三阶段：Windows 日常使用与发布可追溯

- 增加轻量启动检查/诊断入口，报告实际配置文件、监听地址、端口、版本与提交、三条下载链路的代理选择。
- 提供清晰的本机和局域网配置方式，普通运行与详细诊断都采用脱敏输出。
- 明确 NONE/SYSTEM/显式代理语义；诊断错误时能看到实际代理选择。
- 让 Windows/Linux 发布包有启动与转换冒烟检查；依赖使用可复现版本。
- 修正 Docker 从原项目重新克隆源码的路径，确保使用当前 fork checkout，产物提交与实际修复一致。

验收：干净环境可按文档启动并完成本地模拟订阅转换；端口冲突与代理失败可定位；各产物的版本可关联当前 fork 提交；Docker 模拟订阅检查包含本次 403 修复。

### 第四阶段：轻量 Web 转换入口

- 参考 [ACL4SSR](https://acl4ssr-sub.github.io/) 与 [histion](https://histion.github.io/clash/) 的基础/进阶表单、配置选择和链接操作。
- 第一版包括订阅输入、目标格式、Clash.ini 等预设、参数选择、诊断、实际转换预览和复制链接。
- 支持从已有转换 URL 还原参数，复用现有后端参数与转换行为。
- 建议与后端同源分发，适配 Windows 包和 Linux/Docker，避免用户额外指定不清楚来源的转换服务。
- 页面明确区分“已生成转换链接”和“后端实际转换成功”，诊断复用前期能力。

验收：生成链接与原参数行为一致，能还原已有 URL；预览读取真实转换结果；转换失败显示前期诊断信息；局域网设备能访问用户选择的本服务地址。

## 后续候选

- 对用户实际用到的协议增加字段保真回归，优先检查 Trojan 的 SNI/WebSocket Host、Hysteria2 速率和 AnyTLS 类型分组等现有问题。
- 下载 HTTPS 证书验证与按源站例外应单独验证，特别是 Windows 信任库和代理 CA。输出节点的 skip-cert-verify 与下载源验证不是同一设置。
- 若后续需要服务端保存订阅、固定分享档案或跨设备管理，再讨论凭据存储、访问边界、更新历史与迁移；它们不属于用户选定的 Web 第一版。
- 根据实际客户端再评估 rule-providers；它可能缩小转换结果并转移规则更新工作，但需验证客户端支持及规则匹配语义。

## 当前产物与验证边界

[详细分析](optimization-review.md) 保存源码证据与复现边界，[术语表](../GLOSSARY.md) 保存领域用语。本轮已完成四阶段实现：下载可靠性与诊断、受控并发与缓存语义、启动/发布检查、同源 Web 转换入口。

详见 [使用文档](usage.md) 和 [实施验收记录](implementation-validation.md)。Linux 已构建完整应用，使用本地模拟订阅验证 403、无效内容、超时、断流重试、缓存保留、强刷/过期/旧版选择、并发与规则顺序、代理失败、端口冲突和配置格式；没有使用私人订阅。

性能记录使用实际 Clash.ini 中 25 个远程规则条目的顺序，7 个本仓库规则原文约 3.56 MB，其余外部源用明确标记的模拟规则代替；本地 HTTP 每份规则固定增加 50ms 延迟。仅证明该受控条件下的效果，不等同于 Windows 或 GitHub 网络实测。当前测量显示网络占主导，处理结果/完整输出缓存暂不实施，仍为有测量依据后再考虑的候选。

Windows/Linux/macOS 发布脚本已加入打包前模拟转换检查，但本轮未实际运行 Windows/macOS 发布流水线。Docker 已使用当前 checkout、固定源码依赖及构建测试，拉取基础镜像时遭 Docker Hub 429 限流，因此未产出经过本轮验证的镜像。
